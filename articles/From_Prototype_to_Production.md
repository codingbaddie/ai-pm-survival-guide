# 🌉 從 Prototype 到 Production：為什麼 AI 寫好的 Code，工程師還要開發兩週？(2026 改版)

[🇺🇸 English](./From_Prototype_to_Production_EN.md) · *Last reviewed: 2026-10*

*(寫給所有崩潰的 PM 的「防身術」，也適合轉發給以為「AI 已經寫好 Code 了」的主管。)*

> 📝 **改版說明**：第一版的結論是「AI 幫你從 0 走到 60 分，60 到 100 分還是要靠工程師」。到了 2026 年，Agent 也會寫測試、處理錯誤、接資料了，**這條線往後移了很多**。但「原型幻覺」沒有消失，只是換了地方出現。

## 「這不是都跑得動嗎？為什麼不能上線？」

你一定遇過這個情境：
你用 AI 做出了一個超精美的網頁，按鈕會動、圖表會跑，連手機版都調好了。
你興沖沖拿給工程師看：「AI 都寫好了，明天能上線嗎？」

工程師的眼神死掉了：「這個要兩週。」

你心裡想：「AI 兩分鐘就寫出來了，你在唬我？」

---

## 🦄 原型幻覺 (The Prototype Illusion)

殘酷的真相：**在空白環境裡長出來的 Code，是在「無菌室」長大的寶寶。**
它完美、乾淨，但一碰到你們公司累積多年的既有系統，沒穿防護衣就會出事。

這就是 **「整合債 (Integration Debt)」**：

1.  **它是孤兒，沒有真實資料 (Data Context)**：圖表數據是 AI 捏造的 `const data = [...]`。真實的資料散在各個資料庫和老系統裡，格式不一、還有權限問題。「挖通水管」比畫圖難十倍。
2.  **它不知道家規 (Design System & Conventions)**：它用 `blue-500`，公司規範是 `#0F4C81`；它的 Class Name 跟既有的衝突，首頁按鈕突然變形。
3.  **它沒買保險 (Error Handling & Security)**：真實的使用者會輸入 Emoji 當帳號、會斷網、會惡意打 API。

## 🔄 2026 年，什麼變了？

### ✅ 變好的：很多「60 → 80 分」的工作 Agent 也能做了
如果 Agent 是**在你們真實的 Repo 裡**工作（而不是在聊天視窗的空白畫布上），上面三個問題有很大一部分可以提前解決：
*   它會讀到既有的 Design System 和元件，直接沿用。
*   它可以照著現有的 API 和資料結構去接，而不是自己捏假資料。
*   你可以要求它補測試、補錯誤處理，甚至請它先做一輪 Code Review。

所以我現在的第一原則是：**Prototype 一開始就在真實的 Codebase 上做**（細節見 [AI 原生工作流指南](./AI_Native_Workflow_Guide.md)）。

### ⚠️ 沒變的：最後那 20 分，依然是人類的判斷
Agent 寫得出 Code，但這些事它沒辦法替你們負責：
*   **決策**：資料模型這樣設計，三年後還撐得住嗎？這是單向門還是雙向門？
*   **邊界情況與商業規則**：退款、併單、權限例外……很多規則只存在資深同事的腦袋裡，從來沒寫下來。
*   **上線風險**：監控、逐步放量、出事怎麼回滾、資安與個資審查。
*   **Review 的成本**：AI 一天能產出的 Code，超過一個人一天能好好審的量。**瓶頸從「寫」變成了「審」**。

> 2025 年的整合債是「Code 不知道環境」。
> 2026 年的整合債是「Code 產得太快，人類的理解跟不上」。

## 🛡️ PM 該怎麼做？

### 1. 換一個說法
下次拿 Prototype 去找工程師時：

> 「這是我在 **我們的 Repo 上**用 Agent 做的 POC，開在 `poc/xxx` 這個 branch。
> 它有接到真實的 API，也跑過基本測試，但我還沒處理 [權限 / 錯誤情境 / 監控]。
> 想請你們看看：哪些可以直接用、哪些要重寫？上線前還缺什麼？」

這句話傳達了：
1.  **我懂行**：我知道 POC 不等於 Production。
2.  **我有做功課**：我盡量把 Agent 能做的先做完了，你們不用從零開始。
3.  **我尊重**：最後的品質判斷是你們的，我是來討論落地的。

### 2. 把 Review 變輕鬆
既然瓶頸是「審」，PM 能幫上最大的忙就是讓審的人輕鬆：
*   **改動切小**：一個 PR 一件事，而不是一包「AI 一口氣改了 40 個檔案」。
*   **寫清楚 Why**：PR 描述裡寫商業脈絡和取捨，讓工程師審的是邏輯，不是猜你的意圖。
*   **附上驗證證據**：截圖、測試結果、你自己點過的流程。

### 3. 把「兩週」拆開來看
問工程師：「兩週裡面，哪些是整合、哪些是審查、哪些是上線準備？」
你會發現有些項目你可以用 Agent 先幫忙，有些則是一定要人類花時間的。這比爭論「為什麼這麼久」有用多了。

## 結語

AI 是加速器，不是魔法棒。
它讓「做出一個會動的東西」變得幾乎免費，也因此讓**判斷、整合、負責**變成最稀缺的能力。
好的 PM 不是逼工程師更快，而是讓「做出來」和「能上線」之間的距離越來越短。

*如果你也是那個夾在老闆期待與工程現實中間的 PM，轉發這篇，或許能救你一命。*

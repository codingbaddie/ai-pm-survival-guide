# 🧩 把 PM 的工作流程做成 Skill：從「會用 AI」到「為團隊打造 AI 能力」

[🇺🇸 English](./Skills_as_Product_EN.md) · *Last reviewed: 2026-10*

> 會寫 Prompt 是個人技能。**把團隊的流程做成 Agent 可以重複執行的 Skill，是產品能力。**
> 這篇記錄我怎麼把自己和團隊每天在做的 PM 工作，一個一個做成 Skill，以及過程中學到的設計原則。

## 為什麼是 Skill，不是 Prompt？

我以前會在 Notion 存一堆「好用的 Prompt」，要用的時候複製貼上。問題是：
*   **只有我會用**。同事不知道有這段 Prompt，也不知道什麼時候該用。
*   **每次都要記得貼**。忘了貼，品質就掉回原點。
*   **改了沒人知道**。我改進了 Prompt，別人手上還是舊版。

**Skill** 是一個資料夾，裡面的 `SKILL.md` 寫著「什麼情況下要用」和「怎麼做」。Agent 會依照描述**自己判斷**什麼時候載入。把它放進團隊共用的 Plugin，所有人就拿到同一個版本，也能一起改。

> Prompt 是筆記；Skill 是產品。產品有使用者、有觸發情境、有版本、有迭代。

## 我做了哪些 Skill

我的原則是：**先挑「重複、有標準、但很耗腦力」的流程**。

### 1. 需求的「兩端」：BRD 撰寫 × BRD 審查
這是我最有成就感的一組，因為它解決的是**跨部門溝通**，不只是我個人的效率。

| | **BRD Writer**（給業務 / 專業服務單位） | **BRD Reviewer**（給 PM） |
|:---|:---|:---|
| **痛點** | 需求方不知道 PM 需要什麼資訊，丟來一句「我們需要一個報表」 | PM 收到 BRD 後要花大量時間來回追問 |
| **Skill 做什麼** | 用**訪談式追問**，把模糊的痛點轉成 PM 能決策的 BRD；也能自我複查有沒有缺漏、矛盾 | 站在 PM 的角度找資訊缺口，產出**可以直接發給需求方的補件問題清單**；多份 BRD 一起看時，找出**跨需求的撞車議題** |

**關鍵設計**：兩個 Skill 用的是**同一套「好的 BRD 長什麼樣」的標準**。需求方在寫的時候就被引導去回答 PM 會問的問題，PM 審的時候用同一把尺。等於把「需求品質」的定義變成雙方共享的合約。

### 2. 需求收斂：從一句話到一張票
「我想提一個需求」→ Skill 用**一問一答**的方式，一步步追問背後真正的問題，收斂出一份需求摘要。
**使用者明確說「確認」之後，才會在任務系統裡開票。**

### 3. 圖文使用手冊：Agent 自己去看產品、自己截圖
用瀏覽器自動化實際操作正式環境，截取真實畫面，維護一份 Markdown 當作唯一的原始檔，再匯出成 Word 給需要的人。PRD 一更新，就能請它同步手冊。

### 4. 讓非工程師也能發 PR
很多同事改得了文件或設定，卻卡在「怎麼開分支、怎麼推、PR 要發到哪」。這個 Skill 會檢查權限、開分支、照 Repo 的範本寫 PR 描述，**推送前一定先讓使用者確認**。

### 5. 團隊共用規範：個資與資料使用
這個 Skill 不做任何「任務」。它的工作是在任何人處理會員資料、做報表、寫 SQL 的時候**自動被載入**，提醒哪些欄位不能出現、資料要怎麼最小化、有問題該找誰。
**把合規做成預設值，而不是期待每個人都記得。**

## 設計 Skill 的 6 個原則（踩坑換來的）

### 1. `description` 就是你的觸發條件，要寫得像使用者講話
Agent 是看描述決定要不要用這個 Skill。我一開始寫「協助產出商業需求文件」，結果大家說「幫我看這份需求還缺什麼」時完全不會觸發。
後來我把**使用者真的會說的話**（中英文、口語、縮寫）都列進去，觸發率才上來。

### 2. 有副作用的動作，一律等人類說「好」
開票、發 PR、發訊息、推送……只要會影響到別人，Skill 裡就寫死「先給使用者看，等確認」。
這就是 [分級介入模型](./Boundaries_with_AI_ZH.md) 的 Tier 1，只是做進了流程裡。

### 3. 一個 Skill 一個使用者
BRD 撰寫和 BRD 審查，一開始我想做成同一個。後來發現**使用者不同，語氣和要追問的事就完全不同**：對需求方要引導、要白話；對 PM 要直接、要結構化。拆開之後兩邊都好用很多。

### 4. 共用的規則抽出來，變成「規範型 Skill」
個資規則原本散落在報表、SQL、發佈頁面等好幾個 Skill 裡，改一處就要改五處。抽成獨立的規範 Skill 之後，其他 Skill 只要說「處理資料前先讀它」。**跟寫程式一樣：不要複製貼上，要抽共用模組。**

### 5. 從失敗案例迭代，而不是一開始寫到完美
每次 Skill 產出不如預期，我就把那個案例記下來（用 [Magic Tunnel](./Magic_Tunnel_Workflow_ZH.md) 的 `capture-learning`），累積幾個之後一次修正。**Skill 的品質是從真實使用裡長出來的。**

### 6. 寫給 Agent 看，也要寫給同事看
`SKILL.md` 本身就是這個流程最好的文件。新同事讀它，就知道「我們團隊的 BRD 標準是什麼」。**一份文件，人和 AI 都在用，就不會過期。**

---

## 結語：AI Native PM 的工作單位變了

以前 PM 的產出是**文件**：PRD、規格、會議紀錄。
現在多了一種產出：**能力**。把一個流程做成 Skill，等於把我的判斷變成整個團隊每天都能用、而且會越用越好的東西。

> 我衡量自己 AI Native 的程度，不是看我自己用 AI 多快，而是看**我離開之後，團隊還能不能用我留下的 Skill 繼續把事情做好。**

*這個 Repo 裡就有兩個可以直接拿去用的範例：[`capture-learning`](../skills/capture-learning/SKILL.md) 和 [`process-inbox`](../skills/process-inbox/SKILL.md)。*

# 🧩 把 PM 的工作流程做成 Skill：從「會用 AI」到「替團隊做出 AI 能力」

[🇺🇸 English](./Skills_as_Product_EN.md) · *Last reviewed: 2026-10*

> 會寫 prompt 是個人技能。把流程做成 Agent 能重複跑、別人也能裝來用的 skill，是產品能力。

我從 2026 年 2 月開始做自己的第一個 skill，到現在手上有四個在用，其中一個已經進了公司的 plugin marketplace，業務單位真的拿去寫需求。這篇記錄我怎麼做、怎麼迭代，還有踩過的坑。

## 為什麼是 skill，不是 prompt

我以前也是把好用的 prompt 存在 Notion，要用再複製貼上。問題很明顯：

- 只有我會用。同事不知道它存在，也不知道什麼時候該用。
- 忘了貼，品質就掉回原點。
- 我改好了，別人手上還是舊版。

Skill 就是一個資料夾，裡面的 `SKILL.md` 寫「什麼情況要用」跟「怎麼做」。Agent 會看描述自己判斷要不要載入。放進團隊的 plugin，大家拿到的就是同一個版本。

我覺得 prompt 是筆記，skill 是產品。產品有使用者、有使用情境、有版本、要迭代。

## 我做了哪些 skill

| Skill | 誰用 | 做什麼 |
|:---|:---|:---|
| **PM consultant** | 我自己 | 讓 Claude 用資深 PM 的方式跟我討論：每個建議附 trade-off、先對齊再動手、主動 challenge 我 |
| **manual-writer** | 我自己 | 用瀏覽器實際操作 PROD、截真實畫面，維護一份 Markdown 當 source of truth，再匯出 Word 給需要的人 |
| **brd-writer** | 業務 / 專業服務單位 | 用訪談的方式追問，把一句「我們需要一個報表」變成 PM 能拿來做決策的 BRD |
| **brd-reviewer** | PM | 收到 BRD 之後挑出缺口，產出可以直接發給需求方的補件問題清單；多份 BRD 一起給，會抓出彼此撞到的地方 |

最有感的是 brd-writer 跟 brd-reviewer 這一組，因為它解決的不是我個人的效率，而是跨部門的溝通成本。

## 一個需求的兩端：為什麼拆成兩個 skill

一開始只有 brd-writer。用了一陣子我發現，我把「PM 怎麼審 BRD」也塞進去了。但用的人根本不同：

- 需求方要的是引導，要白話，要知道下一題該回答什麼。
- PM 要的是直接、有結構，一眼看到缺什麼。

所以拆成兩個。而且我刻意**不讓兩邊共用同一份 checklist**：

- brd-writer 的 checklist 是**技巧導向**：怎麼問，才問得出答案。
- brd-reviewer 的 checklist 是**症狀導向**：文件長什麼樣子，代表當初沒問到。

同一件事，站的位置不同，要檢查的東西就不一樣。硬塞成一份，兩邊都不好用。

另外 brd-reviewer 有兩個刻意的設計：

1. **不要求需求方回頭改 BRD 原文。** 答案記在問題清單裡就好。要需求方改原文，等於要他做跨章節對帳，那是 PM 寫 PRD 時的工作，不該做兩次。原始 BRD 保持原樣反而有價值，它記錄了需求方原本怎麼想。
2. **分清楚「需求方要補的」跟「PM 自己要判斷的」。** 開發成本、技術可行性、要不要分期、多份需求怎麼整合，這些是 PM 的事，不會包裝成問題丟給需求方。

## 我怎麼迭代一個 skill

brd-writer 從 8 月上線到現在改了 7 輪。每一輪都是同一個 loop：

1. **只用真實證據觸發。** 一份需求方真的用 skill 寫出來的 BRD、我自己在 Google Doc 上的 PM 批註，或是我對上一輪修正不滿意的地方。「感覺可以更好」不算。
2. **先拿 skill 自己寫的規則去對。** 是規則沒寫到，還是寫了但 Agent 沒照做？
3. **每個缺口先分類，再想怎麼修。** 這是需求方本來就該補、只是沒被問到的？那就加一個追問技巧。還是其實是 PM 該自己判斷的？那就不要變成需求方的問題，直接改設計。
4. **修法要具體。** 不是加一句「請注意 XX」，而是寫成一個有名字、有步驟的技巧。

舉幾個真實的例子：

- **自我複查要「憑證據」，不能「憑記憶」。** 我原本以為 AI 在同一個對話裡檢查自己的產出沒用，因為問它「我有沒有問到 X」，它永遠會說有。後來發現問題不在 context 有沒有隔離，而在題目怎麼問。「把第 1 節每個動詞列出來，看後面有沒有跟著具體動作」這種題目，它騙不了自己。所以複查清單每一條都改寫成「檢查動作 → 不通過長什麼樣 → 怎麼補」。
- **新對話就是免費的第三方審查。** 需求方用的是網頁版，沒有 subagent。所以 skill 在他剛拿到成果、心情最好的時候，直接印出一段可以貼進新對話的指令，讓另一個乾淨的 Claude 來審。
- **篩選條件寫錯，比沒寫還糟。** 多方會議議程的篩選原本是「單方答不出來的議題」。結果 PM 自己要決定的事（系統怎麼規劃、優先級）也符合這個條件，照樣被排進會議。後來改成三段：單方能答 → 問題清單；要兩邊一起才能答 → 會議議程；本來就是 PM 的決定 → 哪裡都不放。
- **「誰偵測」跟「誰執行」要分開寫。** 規則表只有一欄「負責角色」，讀起來像是營養師要自己判斷誰請假超過 20 天。但人工偵測正是這個需求要消滅的痛點。
- **別叫使用者做他的環境做不到的事。** skill 裡寫了「存成 Markdown 檔到工作目錄」，網頁版根本做不到，需求方直接卡住。
- **每個數字標來源。** 〔實測〕〔估計〕〔待查〕。PM 看到估計值，就知道哪些要先查證再拿去做決策。

另外，進公司 plugin 的那一份，每次改版都是開 PR 給工程師 review 才上線。plugin 的名稱也是照 review 的建議，從綁定單一 skill 的名字改成依使用者族群命名，之後其他給業務單位的 skill 才能放在一起。

這個 loop 是我跟 Claude 在前幾輪摸出來的。後來我直接叫它「把這次迭代的過程學起來」，寫進 memory，之後迭代其他 skill 也照這套跑。

## 做 skill 學到的事

**skill 不是常駐人格。** 我的 PM consultant skill 一開始放在 skills 資料夾，我以為 Claude Code 每次對話都會自動套用。結果不會，skill 要被觸發才會載入。後來我把「每次都要遵守」的核心規則搬到專案的 `CLAUDE.md`，細節模式留在 skill 裡，需要時再去讀。**always-on 的東西放 CLAUDE.md，按需取用的放 skill。**

**description 就是觸發條件，要寫得像使用者講話。** Agent 是看描述決定要不要用。我把需求方真的會說的話都寫進去：「幫我看這份 BRD」「這份還缺什麼」「review BRD」「兩份需求撞到」。

**還沒發生的問題，先不要蓋基礎建設。** brd-reviewer 本來想順便做一份「需求登記簿」，記錄每份 BRD 動到哪些人、哪些系統，新的進來就自動比對。最後我決定先不做：兩三份 BRD 用讀的就夠了。我把設計跟觸發條件寫在 README 裡，等我開始覺得「這份好像跟之前哪一份有關，但我要回去翻」的時候再做。

**先搞清楚使用者在什麼環境。** 我想讓需求方寫完 BRD 之後再做一次第三方審查。直覺是派一個 subagent 去審，但需求方用的是 Claude Chat，不是 Claude Code，根本沒有 subagent。所以改成在同一個對話裡引導他們開一個新的對話來審。

**授權範圍要事先講清楚。** 有一次我請 Claude 幫我新增 brd-writer，它順手把我原本的 PM skill 也改了，還 push 上去了。從那之後我開工前都會先講：這次只能新增什麼、哪些東西不准動。能 push、能開 PR 的 Agent，每一步都要有確認點。

## 結語

以前 PM 的產出是文件：PRD、規格、會議紀錄。現在多了一種產出，是**能力**。把一個流程做成 skill，等於把我的判斷變成團隊每天都能用、而且會越用越好的東西。

我自己衡量 AI native 的方式，不是看我用 AI 多快，而是看我不在的時候，團隊能不能用我留下來的 skill 繼續把事情做好。
